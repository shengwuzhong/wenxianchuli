# GUI 工作台 P3：自动导入与主操作收敛

P3 的目标是把「把 PDF 放进 uploads，再回界面点一堆按钮」改成：

- 新 PDF 放进当前区的 `uploads`，工作台自动发现、校验、排队、解析；
- 表格里未跑/异常的文件排在最前；
- 第一层只保留一个主操作，复杂重跑收进「更多」。

## 1. 自动导入的边界

| 区 | 监听目录 | 输出目录 |
| --- | --- | --- |
| 区 A · 主库 | `uploads/` | `out/` |
| 区 B · 分库 | `zones/zone_b/uploads/` | `zones/zone_b/out/` |

只监听本区目录，不监听桌面拖拽窗口；GUI 窗口的拖拽不是 P3 的入口。

### 首次启动先建基线

每个区第一次启动 P3 时，会把 `uploads` 里已经存在的 PDF 记为 **baseline**（基线），
并明确写日志：

> 首次建立基线 N 篇；既有文件不自动跑。

原因是历史积压可能上百篇，自动全跑会突然消耗大量 Paddle 页数。
基线文件仍可在表格里全选后点「开始解析」手动处理。

### 新文件才自动跑

基线之后，只有**基线里没有的新文件**进入自动流程：

1. 连续两次扫描到相同大小、相同 `mtime_ns`，认为文件已写完；
2. 计算 SHA-256；
3. SHA 已在别的文件名下出现 → `重复文件`，不提交；
4. 同名文件内容变了 → `同名冲突`，不覆盖；
5. 0 页/打不开 → `无法打开`，不提交；
6. 正常 → `等待自动处理`，随后按账号和额度提交。

文件夹里的非 PDF、子目录、临时文件一律忽略。

## 2. 状态与排序

| 状态 | 含义 | 自动提交 |
| --- | --- | --- |
| `未跑` | 有 PDF，无输出 | 否（历史/手动） |
| `等待自动处理` | 新文件已识别，等待提交 | 是 |
| `排队中` | 已进入 Runner 队列 | 已提交 |
| `运行中` | 子进程正在跑 | 已提交 |
| `等待额度` | 当前账号今日剩余页数不够 | 否 |
| `等待账号` | 当前账号没有 Paddle token | 否 |
| `已暂停` | 发现新文件时工作台处于暂停 | 继续后处理 |
| `待确认` | 超过批量阈值且用户取消，或提交失败 | 手动 |
| `同名冲突` | 同名 PDF 内容变化 | 否 |
| `重复文件` | SHA 与已有文件相同 | 否 |
| `无法打开` | 0 页/解析失败 | 否 |
| `部分异常` | 有产物但缺渠道/元数据 | 否（走重跑） |
| `已完成` | 有 `index.html` 且渠道齐全 | 否 |

排序固定为：未跑/等待自动处理 → 排队/运行 → 等待额度/账号 →
冲突/坏/重复 → 部分异常/未完成 → 已完成。未跑组内按导入时间倒序。

## 3. 自动提交前检查

`_submit_ingest` 按以下顺序检查：

1. 文件还在，且当前 Runner 没有同文档任务；
2. 当前区账号有 token；
3. 本批总页数 ≤ 当前账号今日剩余页数，否则整批标记 `等待额度`；
4. 单批 ≥ 50 篇或 > 5000 页时弹一次确认；取消则标记 `待确认`；
5. 每篇按 `区/文档` 预占 Paddle 页数，然后提交完整 `stages.ORDER`。

额度预占是**提交前记账**，不是从 AI Studio 实时查询。页数无法读取时不会提交。

## 4. 主操作收敛

第一层只保留：

- `开始解析 ▾`：智能主操作；
- `更多 ▾`：快速重跑（跳 NER）、重跑缺口、重试缺失渠道、执行选中阶段、
  字段/实体审计、全选；
- 查看器 / 结果总览 / 归档。

`开始解析` 的行为：

| 选中情况 | 动作 |
| --- | --- |
| 全部未跑/未完成 | 全流水线 |
| 全部缺渠道 | 只补缺失渠道 |
| 全部已完成 | 打开结果 |
| 混合/已有产物 | 使用当前勾选的阶段 |

没有选中任何文档时给明确提示，不再静默返回。

## 5. 额度口径（为什么 AI Studio 可能显示 0）

本地账号行的 `Paddle x/20000` 是**本工作台的预占账本**，记录的是本地提交时预留的
PDF 页数，不是 AI Studio 的服务器账单，也不会回填历史调用。

AI Studio 页面的「今日调用解析页数」是**按登录账号 + 模型标签**统计的。当前配置：

- 实际请求模型：`channels.json` 的 `paddle_api.model = PaddleOCR-VL`；
- 令牌：`.workbench/accounts.json` 的 `primary`（本机账号）或 `pp`（wayjoe）；
- AI Studio 截图选中的标签是 `PaddleOCR-VL-1.6`。

因此 0 的常见原因是：浏览器登录的不是实际使用令牌对应的账号，或选中的模型标签与
实际请求模型不一致。核对顺序：

1. 在「账号与额度…」确认当前区账号 key 和 token 尾号；
2. 用同一账号登录 AI Studio，切到实际模型标签；
3. 刷新页面，再看今日页数；
4. 必要时在账号页确认令牌所属账号，而不是只看令牌前缀。

## 6. 回退

P3 的代码回退点：

```powershell
git reset --hard 974af94
```

或只回退 P3 提交：

```powershell
git revert --no-edit d4e3662
```

回退前先关闭 GUI，避免旧进程继续写 `.workbench/ingest.json`。

## 7. 验证

```powershell
py -3.11 -m py_compile gui.py ingest.py
py -3.11 -m unittest -q test_ingest.py test_workbench_accounts.py test_workbench_state.py test_field_audit.py test_pipeline.py
```

P3 验证重点：

- 首次启动只建基线，不自动跑历史文件；
- 新文件两次稳定扫描后才进入 `pending`；
- 重复 SHA、同名内容变化、0 页文件不提交；
- 暂停时新文件进入 `已暂停`，继续后处理；
- 超过 50 篇/5000 页只弹一次确认。
